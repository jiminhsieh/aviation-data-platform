# Design

## Context

See `proposal.md` for the motivation and the four capability specs for the behavior contract. Today `infra/tf/` contains only a README; `ingestion/` and `transformation/` are separate, clean Git submodules containing READMEs and the same one-poll JSON fixture, not application code. The root README favors Azure Southeast Asia, AKS, Strimzi Kafka, ADLS Gen2, Key Vault and Databricks. The exercise requires the fixed OpenSky region, registered OAuth2 credentials, a live self-service last-24-hours country view, and a runnable Git repository. The `references/thales-data-platform-architecture.md` diagram is background for a larger platform, not a mandate to install Airflow, Trino, DataHub, etc.

## Goals / Non-Goals

**Goals:** One demonstrable `sit` environment with parameterized resource names for `uat`/`prod`, end-to-end replay/retry behavior, explicit permissions, and no cloud resources created outside tracked IaC/deployment assets. Minimize idle cost *within the stack already chosen in the repo*. Run the two transformation implementations independently testable but in a single ordered streaming job.

**Non-Goals:** Additional sources, a general schema registry, automatic CI/CD, multi-region HA, full production IAM/network isolation, per-minute storage partitions, and an always-on BI frontend. Do not claim all three environments are running for the demo.

## Decisions

### 1. One connected Azure foundation and a private broker listener

`infra/tf/` defines the resource group, VNet/subnets and NSGs, AKS with OIDC/workload identity and Key Vault CSI support, ACR, ADLS Gen2 lake/checkpoint storage, Key Vault, a VNet-injected Databricks workspace, Unity Catalog metastore assignment/access connector/catalog/schemas/grants, and an auto-stopping SQL warehouse. Terraform installs Strimzi via Helm and a small repository-owned Helm release for a one-broker, persistent-volume KRaft Kafka cluster/topic/users. Kafka's internal Azure Load Balancer bootstrap and broker listeners are reachable from Databricks on the shared VNet; TLS and SCRAM protect the connection. Use a single source-specific `opensky.states.v1` topic and separate lake prefixes/tables so a second source can reuse the foundation. Stage workload deployment after infrastructure: build/push the scraper image to ACR and deploy its CronJob using checked-in manifests/chart; point the Databricks job at the pinned `transformation` submodule commit. The Terraform outputs, deployment commands, and workload/job definitions must be reproducible from Git (not manually created in a UI).

The PoC uses separate local Terraform state per environment, explicitly ignored by Git, and documented teardown; never put external credentials in TF variables/state. Moving to an encrypted, access-controlled ADLS remote backend is a prerequisite for real shared/prod deployment. Public HTTPS endpoints for ADLS/Key Vault are permitted with identity-based authorization and no anonymous blob access; there are no private endpoints as suggested in the repo README. Alternatives: Event Hubs or Container Apps + serverless ETL would reduce Kafka/AKS operations/idle spend, but would not exercise the stated AKS/Strimzi/Databricks design; revisit if team size or budget cannot support it. One Kafka broker is **not** production HA.

### 2. Authenticated collection with a cadence that CronJob actually supports

`ingestion/` adds a small Python CLI, pinned dependencies, Dockerfile, a versioned `.avsc`, and fixture-based tests. A Kubernetes CronJob runs `*/2 * * * *` UTC with `concurrencyPolicy: Forbid` and a bounded job deadline. Each run gets an OAuth2 client-credentials token, makes **one** states request for `lamin=-11&lamax=21&lomin=92&lomax=141`, validates `time` and the 17-element state arrays, emits one Avro poll record keyed by response time, and waits for Kafka delivery acknowledgement before success. Nullable fields use typed Avro unions. On `429` (including `Retry-After`), timeout, auth failure or 5xx, log a redacted failure and skip the run; do not repeat the states request within that run. At 720 polls/day × 4 credits = 2,880 credits/day, this stays under the documented 4,000-credit registered budget even if the API is already throttled. A 90-second CronJob schedule is not supported; choose two minutes rather than an always-running scheduler.

OpenSky client ID/secret are created outside the platform, then written into Key Vault by a documented secret-injection step (not TF); AKS workload identity + CSI mounts them only into the collector. Strimzi creates a restricted producer KafkaUser secret mounted by the collector alongside the cluster CA certificate. A documented, non-logging deployment script synchronizes the restricted consumer KafkaUser secret and broker CA certificate to Key Vault for Databricks TLS/SCRAM access. The Databricks job reads only these broker credentials from a Key Vault-backed secret scope; the access connector identity writes the three lake layers and checkpoints. Document rotation/restart steps. Human roles use Unity Catalog grants, not direct storage permissions: ATM silver/gold SELECT, data scientist silver/gold SELECT + SQL usage (their own sandbox if they need to write), platform engineer maintenance on all three layers; no analyst gets raw or secret access. Alternative: anonymous scraping cannot sustainably meet the freshness target; direct secret literals in Kubernetes/Terraform are not acceptable.

### 3. Avro bytes archived in raw; keyed silver built from the same batch

The producer publishes schema-versioned Avro *datum* bytes for a poll record (`schema_version`, response `time`, an array of named/typed fields for all 17 state positions). The canonical v1 schema is mirrored into each independently clonable submodule, with a root contract test that fails if they diverge. Schema changes require an explicit new version and corresponding decoder; unexpected versions/invalid decode fail the batch rather than silently reinterpret bytes. The raw Unity Catalog external Delta table stores **the exact Avro bytes** in a binary column plus topic/partition/offset, response time, and receipt time. Delta is the table storage format; the archived payload is still Avro, not the original JSON whitespace. Keep raw for replay beyond the Kafka topic's short retention (e.g. seven days). Do not expire raw automatically in this PoC.

`transformation/bronze_silver` reads Kafka via Spark Structured Streaming with a one-minute trigger and durable ADLS checkpoint. In `foreachBatch`, first idempotently MERGE raw on `(topic, partition, offset)`, then decode and flatten each poll, validate non-empty `icao24` and coordinate bounds, trim callsign, leave genuine null positions/altitudes intact, and insert-only MERGE silver on `(response_time, icao24)`. Deduplicate same-key values deterministically by Kafka coordinates before MERGE; first accepted observation wins on later replays. Count/log rejected rows and publish table/column descriptions; keep their parent poll in raw. Silver has typed event/position/contact timestamps, coordinates and altitude with nullable types. Partition lake tables coarsely by UTC date and use Delta MERGE, not minute-partition overwrite: 250k rows/day makes minute-sized files and blind overwrite unsafe for retries. Alternative: separate streaming sinks/checkpoints make raw/silver consistency and failure recovery harder at this PoC size.

### 4. Silver-to-gold is a distinct module invoked after silver commits

`transformation/silver_gold` accepts the affected `(UTC response hour, normalized origin_country)` keys from the batch, re-queries silver for each touched hour/country, and MERGEs the resulting aggregates into gold. In silver, blank/missing origin country is labelled `Unknown`. Gold records hour start, origin country, `count(DISTINCT icao24)` as `aircraft_count`, mean of non-null `geo_altitude` observations as `avg_geo_altitude_m`, observation and non-null-altitude counts for transparency, and latest response time for freshness. The aggregation is per *origin* country, not aircraft position or unique flights. There is no 24-hour data deletion: the last 24 hours are a query filter over retained history. With two-minute collection, one-minute Spark microbatches and small partitions, **target** under five minutes from a successful poll containing valid observations to gold; missed polls, stale upstream responses and job startup/recovery can exceed it. SQL Warehouse auto-stops when unused; authorized users query gold through Databricks SQL without starting a notebook or requesting an engineer.

The single streaming `foreachBatch` calls raw → silver → gold and only then acknowledges its checkpoint; Delta table MERGEs make retries safe even if a later stage fails. This is two independently testable transformation implementations, not two independent always-on jobs. Gold recomputation uses silver as truth, so a retry, duplicate Kafka delivery or late poll corrects affected buckets without a separate watermark or reaggregation of all history. An empty poll advances raw and the checkpoint but has no silver/gold rows; the runbook compares raw and gold latest times to tell that case apart from a stalled job. Alternative: a second silver-to-gold stream with change-data feed would decouple workloads at higher scale, at the cost of another checkpoint, compute and complexity; scan-by-affected-hour is appropriate for the supplied volume.

### 5. Explicit scope, economics and observability

Ship a Mermaid diagram and README/runbook showing setup, smoke test, SQL query, freshness check, failure/replay, permissions, managed vs self-managed choice, and safe teardown. For cost comparisons use the challenge's **960 polls/day × 33 KB ≈ 0.95 GB/month raw JSON** even though the chosen schedule yields 720 polls/day; estimate Azure bills by region/SKU, with AKS node(s)/Kafka disks/load balancers and the continuous Databricks job dominating idle spend (roughly **$800–$2,000/month** if left running; auto-stopping SQL adds usage-based cost; storage is small). State what must be destroyed/paused after the demo. At 100× data (~100 GB/month raw JSON before format/replicas), storage is still not the primary lever: broker capacity, Spark shuffle/hour recomputation, cluster spend and especially OpenSky quota/access become limiting. A licensed feed and scalable partitioning/compute would be needed before claiming 100× live ingestion. Tests use the existing JSON fixtures and local Spark fixture data; cloud smoke tests run only with operator-provided accounts and credentials.

## Risks / Trade-offs

- [Cost and availability] One broker and continuous Spark incur fixed spend and single points of failure → call out expected bill, provide teardown/scale-down instructions and checkpoints/raw archive; no HA claim.
- [Cross-service bootstrap] Strimzi listeners/credentials and Databricks Unity Catalog require tenant/account privileges and ordered setup → pin supported provider/runtime/operator versions, provide a scripted two-stage install with Terraform-managed resources and validate actual private broker reachability before starting jobs.
- [Avro compatibility] Independent submodules can drift → pin v1 in both, compare schema bytes/fields in a root check, test producer → decoder round trip and fail closed on incompatible versions.
- [One job couples sinks] Gold failure pauses raw/silver progress → idempotent MERGEs and source checkpoint retry preserve correctness; split into separate jobs/change feed if gold workload dominates or the lag target fails.
- [Security shortcut] Public HTTPS data/secret service endpoints and local Terraform state are weaker than production isolation → identity-based permissions, TLS, no tracked state/secrets, and plan private endpoints + remote state for production.
- [Source variability] OAuth/quota and stale API timestamps can break freshness independent of processing → distinguish collection time from response time, respect 429, inspect raw and gold watermarks and job status.

## Migration Plan

1. Install submodules; acquire Azure/Databricks admin access and a registered OpenSky OAuth client. Select `sit`, review the cost and data-destroying steps, run Terraform init/plan/apply with an isolated local state, then verify Kafka private connectivity and Unity Catalog grants.
2. Inject external OpenSky credentials into Key Vault via the documented secret command, synchronize the restricted Strimzi consumer secret for Databricks, build/push the pinned collector image, deploy its CronJob, and deploy/start the Databricks job using the committed transformation revision. No manual portal-created resources are part of the path.
3. Run fixture tests, a live smoke test and last-24-hours SQL query; check raw Avro → silver → gold counts, freshness, deliberate batch retry and role access. Commit submodule implementation revisions in their respective repositories, then update root submodule pointers.
4. To roll back an application revision, suspend the CronJob/stream, redeploy the previous image and pinned transformation revision, and resume from the persistent checkpoint. To remove the PoC, stop both workloads, export/preserve any needed lake data and state, and run documented Terraform destroy; warn that deleting storage/checkpoints destroys replay history. Schema changes require versioned readers and an explicit migration, not in-place reinterpretation.
