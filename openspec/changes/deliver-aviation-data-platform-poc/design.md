# Design

## Context

See `proposal.md` for motivation and the four capability specs for behavior contracts. The adopted topology in `references/thales-azure-data-platform-design.md` v1.4 and the root/infra READMEs supersedes this change's earlier Kafka plan: AKS → immutable Bronze Avro → streaming Silver → independently scheduled SQL Gold. `infra/tf/` has no Terraform configuration; the independently versioned `ingestion/` and `transformation/` submodules contain READMEs and fixtures, not runnable applications. Documentation describes a target, not a deployed platform.

The assessment requires the fixed OpenSky region, registered OAuth2 credentials, near-original retention, typed/deduplicated observations and self-service country/time history over at least 24 hours. The broader `references/thales-data-platform-architecture.md` is background, not a requirement to install Kafka, Airflow, Iceberg/Polaris or Trino. The latest PoC state decision is explicit in `infra/tf/README.md`: use local Terraform state, not a mandatory remote backend.

## Goals / Non-Goals

**Goals:** Deliver one demonstrable `sit` environment using reusable inputs for `uat`/`prod`, all in `southeastasia`, with isolated state/data/identities/checkpoints. Make collector, Silver stream and Gold SQL independently deployable and observable. Preserve complete-hour replay correctness, least privilege and reproducible Git-pinned delivery within the assessment's 15–20-hour prioritization budget.

**Non-Goals:** Running all three environments for the demo; a message broker, custom processed-file ledger, Auto Loader, generic connector framework, CI/CD, multi-region HA, production private networking or a polished UI. Do not remove validation, secure identities or data-loss prevention to meet the budget. Runtime sizing and latency/cost claims require measurement.

## Decisions

### 1. Minimal connected Azure foundation with local PoC state

Terraform AzureRM provisions the resource group, VNet/subnets/NSGs, minimal AKS/ACR with OIDC/Workload Identity and CSI support, HNS-enabled ADLS Gen2, Key Vault, Databricks workspace/Access Connector and diagnostics. After workspace availability, the Databricks provider configures metastore assignment where needed, catalog/schemas, storage credentials/locations, Bronze/checkpoint volumes, managed tables, principals/grants and compute. Version-controlled transformation Job definitions bind to those resources; Helm deploys the collector. Avoid managing the same object in both Terraform and Job deployment tooling. External OpenSky registration and secure secret injection are documented manual inputs, not hidden portal-created infrastructure.

Use four containers: `bronze`, `checkpoints`, `lakehouse`, `quarantine`. Bootstrap the stable Bronze directory before starting the explicit-schema stream. Keep checkpoints in a separately governed protected volume, outside discovery and managed-table storage, without automatic expiry. Silver and Gold are managed Delta tables partitioned by `snapshot_hour_utc` and `bucket_hour_utc` respectively; both keys are full-date UTC TIMESTAMPs. Do not manipulate managed-table files or drop/recreate tables during refresh.

The PoC uses **separate local Terraform state per environment to keep setup simple**. Ignore state and secret-bearing variable files in Git; protect and back up local state and document single-operator use. For shared/production deployments, recommend an ADLS Gen2 storage account with Terraform's AzureRM remote backend, restricted access and state locking. Remote state is not a prerequisite for this PoC. Public service endpoints over authenticated HTTPS are permitted with justification, anonymous storage disabled and verified AKS/Databricks connectivity. Production private storage/Key Vault endpoints and DNS, including the separate supported serverless SQL NCC workflow, are deferred.

**Rationale / alternatives:** ADLS is the durable handoff, so no Kafka/Strimzi listener, broker users, disks or credential synchronization are needed. AKS and Databricks retain the selected platform operating model; Functions/Container Apps or scheduled batch could reduce idle cost but are not the adopted topology. Local state avoids remote-backend bootstrap for this PoC, at the cost of local backup and collaboration limits.

### 2. Budgeted collector publishes immutable, source-shaped Bronze

A small pinned Python image in `ingestion/` uses an HTTP client, `fastavro` with Snappy support and the Azure SDK. Its Helm-deployed CronJob runs `*/2 * * * *` in UTC with `concurrencyPolicy: Forbid`, bounded application/pod retries and a short total deadline. Each normal run exchanges OAuth2 client credentials and requests exactly `lamin=-11&lamax=21&lomin=92&lomax=141`. At 720 polls/day × four credits, normal use is 2,880 credits against 4,000; the remaining 1,120 credits/280 extra states calls cover **all** retry layers, validation and other collectors sharing that allowance. Three live environments would use 8,640 credits before retries. Respect `X-Rate-Limit-Retry-After-Seconds` on `429`; log remaining credits when available. Do not equate a two-minute schedule with Gold freshness.

Validate timestamp and all 17 positional fields, then write one Snappy Avro object container with one record containing **only `time` and `states`**. Preserve nullable values, source numeric/boolean types, padded strings and nested sensors. Heterogeneous aircraft arrays need an Avro item union plus per-position validation; do not reshape them into named records or add schema/hash/fetch fields. Schema definitions belong in Git and container headers. Round-trip equality means decoded structure/values, not original JSON or Avro bytes. Contract evolution needs coordinated producer/reader tests, not implicit reinterpretation.

Canonical path: `opensky/states/year=YYYY/month=MM/day=DD/hour=HH/<response.time>.avro`, derived entirely from source time in UTC. For `1793013825`, use `year=2026/month=10/day=26/hour=11/1793013825.avro`. Publish atomically with create-if-absent semantics; an existence check alone is insufficient. If present, compare decoded content: identical is idempotent success; differing content preserves canonical Bronze, quarantines the conflicting original under a unique restricted path, alerts and fails. Invalid original responses also go to quarantine, outside discovery. Valid null/empty `states` is archived. Authentication, secret, storage, collision-read or quarantine failures exit nonzero; no partial final object or false archival success is acceptable.

**Rationale / alternatives:** Source-shaped immutable files are independently replayable without broker retention. Named records or enriched Bronze would simplify decoding but violate the adopted preservation contract. UUID-only paths or overwrite-on-retry would hide conflicts. A 90-second CronJob expression cannot provide the chosen schedule, and increasing polling cannot bypass source quota.

### 3. Native streaming rebuilds complete Silver hours

`transformation/bronze_silver` uses `spark.readStream.format("avro")` with an explicit Spark schema, `recursiveFileLookup=true`, `pathGlobFilter=*.avro`, a stable source root and a dedicated persistent checkpoint. Pin a compatible runtime and test the actual complex-union struct/branch representation before field mapping. A continuous **Databricks Job trigger** maintains one long-running query on **classic Jobs compute**, initially using one-minute processing-time micro-batches. This is not Spark continuous-processing mode; `foreachBatch` requires micro-batches. Serverless Jobs compute is not the selected streaming runtime; a Serverless SQL warehouse for Gold is separate.

In each `foreachBatch`, identify affected source UTC hours **before exploding `states`**. Reread every canonical file in each affected hour with the same batch schema; validate source/path agreement and fail on unreadable or incomplete hours. Capture actual file provenance before flattening and verify metadata support on the pinned runtime. Decode/normalize/validate the complete hours, retaining typed source fields and genuine optional nulls, trimming callsigns only in Silver and leaving missing/blank country unchanged. Reject invalid six-hex ICAO identifiers and out-of-bounds coordinates with restricted file/row diagnostics and counts; propagate accounting failures. Label counts by rebuild scope, since rereads are not newly acquired observations.

The business key is `(snapshot_time, icao24)`, not aircraft ID alone. Choose a survivor by greatest `last_contact`, then `time_position` (nulls last), then a stable normalized observation-content hash with a consistent ordering. The hash is transformation-only. Keep `snapshot_time` as BIGINT; derive hour and five-minute bucket epoch seconds using `floor(snapshot_time / 3600) * 3600` and `floor(snapshot_time / 300) * 300`, then convert to UTC TIMESTAMPs. Configure Spark/SQL sessions for UTC.

Write all rebuilt affected hours in **one atomic Delta overwrite with an explicit `replaceWhere` predicate on `snapshot_hour_utc`**. Keep constraint checking enabled and preserve table/schema/grants. Never overwrite all Silver, use partial-hour input or separately delete/insert. No affected hours means no write; an affected hour with zero valid observations still needs a schema-correct empty replacement to clear that hour only. A null/empty new snapshot must not erase earlier valid observations in the same hour.

Retain complete canonical Bronze for the retained Silver/rebuild horizon, initially approximately 30 days; never rebuild an expired, partly deleted or incompletely restored hour until its source is complete. Serialize stream/backfill writers. Required processing/accounting must succeed before checkpoint acknowledgement; Gold is never invoked in this callback. A commit-before-checkpoint failure rereads/replaces full hours again, preserving business rows without duplicate keys while `processed_at_utc` can change.

**Rationale / alternatives:** Complete-hour replacement handles late files, deterministic survivor corrections and replay without insert-only first-wins behavior. Blind append, partial-hour overwrite and aircraft-only dedup lose correctness. A manifest or key-based MERGE is unnecessary at PoC scale; repeated rereads/rewrites are the deliberate cost, to be benchmarked before optimizing.

### 4. Independent SQL refresh owns Gold correctness

Deploy a version-controlled SQL-file task in `transformation/sql` as a separate Job on a Pro or Serverless SQL warehouse, initially every two minutes UTC with one active refresh. Gold reads a consistent Silver snapshot and uses one whole-table atomic `INSERT OVERWRITE TABLE aviation.gold.aircraft_activity_5m` over **all retained Silver**. Preserve the existing table/schema/grants. Ensure whole-table, not dynamic-partition, overwrite semantics: vanished country groups and hours must disappear, and genuinely empty Silver must clear Gold. No drop/recreate, additive counters, upsert-only aggregate MERGE or separately committed delete/insert.

For each `(bucket_start_utc, icao24)`, select the latest observation for aircraft count and normalized registration-country proxy (`Unknown` for null/blank only in Gold). Independently select the aircraft's latest non-null `baro_altitude_m` within that same bucket, including an earlier value when its latest row is null. Never carry altitude across buckets or weight aircraft by their observation frequency. Group into `aircraft_count`, `avg_baro_altitude_m`, `altitude_sample_count`, `last_source_time` and `updated_at_utc`. Derive `bucket_hour_utc = DATE_TRUNC('HOUR', bucket_start_utc)` in UTC; logical buckets remain five minutes despite hourly physical partitions.

SQL failure leaves prior Gold available while Silver continues. Retry independently; unchanged Silver preserves business aggregates while `updated_at_utc` changes. Retain at least trailing 24 hours after warm-up, initially approximately 30 days. The analyst query uses hour pruning **and** the exact rolling bucket cutoff; 24 hours can span 25 partitions. Document registration country versus geographic location, units and null semantics.

**Rationale / alternatives:** Full recomputation is the smallest complete strategy for historical corrections and stale-group deletion at this volume. A coupled callback would make SQL failures stop Silver; a second Spark stream would add compute/checkpoint complexity. Incremental affected-bucket replacement needs correct deletion semantics and is deferred until full-scan measurements justify it.

### 5. Separate identities, observability and honest economics

Use distinct collector, Silver-stream and SQL Run-as identities. Collector Workload Identity/CSI receives only OpenSky secrets plus Bronze create/collision-read and quarantine write access. Databricks uses the Access Connector and UC storage grants, not storage keys: stream Bronze read/checkpoint read-write/Silver read-modify; SQL Silver read/Gold read-modify/warehouse use. Include catalog/schema usage grants. Data scientists read Silver/Gold; ATM users read Gold and optionally Silver. Analysts have no Bronze/checkpoint/secret or curated-write access. Publish ownership, source URLs, definitions and limits in UC comments and a small dictionary/dashboard. A second source reuses platform resources but needs its own adapter, schema/path, checkpoint and transformation semantics; no connector framework now.

Measure source→fetch, Bronze, Silver and queryable-Gold lags separately, targeting **p95 <5 minutes**, not a per-poll guarantee. Track latest distinct source timestamp, including empty snapshots, stream progress/backlog, affected-hour reread/write metrics, required rejection accounting, commits, SQL success/age and compute uptime. Do not infer health only from Gold aircraft timestamps or a Silver checkpoint. Repeated stale source responses and empty feeds must be distinguishable from failed workloads.

Cost reporting uses current `southeastasia` SKUs and measured AKS nodes, continuous Spark DBUs/VM time and SQL warehouse usage. Budget approximately 730 runtime hours/month for continuously running services; frequent SQL schedules may defeat auto-stop. No verified monthly total exists. Report each environment and active-environment totals. The chosen cadence implies approximately 181,440 observations/day and 0.71 GB/30 days of uncompressed JSON; keep the assessment's 960 polls/day × 33 KB ≈ 0.95 GB/30 days comparison separate. Measure small-file/compression overhead (JSON/Gzip versus Avro Snappy/Deflate), full-hour read/write amplification and Gold full-history scans. There are about 720 Bronze files/day, 30/hour and 21,600/30 days. At 100× volume, distinguish records-per-poll growth from source/file-count growth; OpenSky quota cannot be solved by scaling AKS.

**Rationale / alternatives:** Separate telemetry reflects independent failure boundaries and avoids false freshness/security claims. Unsupported fixed monthly estimates, trigger-only latency calculations and presumed compression savings would misrepresent the implementation.

## Risks / Trade-offs

- [Avro union/runtime compatibility] → Pin and test the real producer-to-Spark path, explicit schema, numeric/boolean branches, sensors, nulls and file metadata before wider deployment.
- [Partial Bronze rebuild erases history] → Protect the full rebuild horizon, verify source completeness and fail before replacement; never treat unreadable/missing inputs as an empty hour.
- [Reread/rewrite and full-scan amplification] → Measure batch duration, bytes and warehouse uptime; introduce incremental processing only with equivalent atomic correction/deletion semantics.
- [Checkpoint loss or file discovery bounds] → Preserve checkpoints across ordinary restarts; test late/new directories and old restored-file behavior; use controlled bounded complete-hour replay when discovery is insufficient.
- [Malformed canonical file blocks progress] → Stop and alert. Any audited exclusion/quarantine continuation needs a deliberate recovery decision; never silently ignore corrupt files.
- [Source quota/staleness/outages] → Share retry budgets, respect throttling and report genuine gaps. The live endpoint's approximately one-hour retrospective window cannot recover arbitrary outages.
- [Eventual Gold consistency] → Monitor and retry SQL independently; checkpoint success is not Gold freshness.
- [PoC security/state limits] → Restrict HTTPS identity access and protect/back up local state; shared/production use needs remote state and validated private connectivity, including serverless networking.
- [Fixed spend and bootstrap privileges] → Verify regional availability/account permissions early, pin provider/runtime/deployment versions and document safe scale-down/teardown; no HA or unmeasured cost claim.

## Migration Plan

1. Initialize submodules, select `sit`, confirm Azure/Databricks bootstrap privileges/SKUs and registered OpenSky quota across live environments. Prepare protected isolated local state; provision foundation, identities, storage, UC volumes/tables/grants and compute. Verify networking and role denials. Do not require a remote backend for this PoC.
2. Inject external OpenSky credentials outside Terraform state. Build/push the collector image and deploy its Helm ServiceAccount/CSI/CronJob. Verify source-shaped hourly Avro, identical/conflicting snapshot handling and visible archival failures before enabling transformations.
3. Deploy/start the pinned continuous Silver Job with approved schema/runtime/checkpoint, then enable the independent Gold SQL task and UTC schedule. Ensure only one writer per table. Run component contract/fixture tests alongside each implementation, then producer-to-Spark integration, atomic overwrite, failure/replay and analyst-access checks.
4. Collect at least one hour of live p50/p95/max stage latency and actual compute/cost evidence. Demonstrate a last-24-hours analyst query after real warm-up or with a clearly labeled fixture. Reconcile the remaining ingestion scheduling wording, transformation hour types/Gold partitioning and stale reference status/state guidance. Add executable commands only when their files exist. Commit each submodule, then advance root pointers and verify a fresh recursive checkout.
5. For ordinary restart, retain the original checkpoint. For explicit historical backfill, pause/verify no Silver writer, expand selected original paths to complete UTC hours, confirm completeness, rebuild using the same transformation, validate Silver, run Gold SQL and resume the original stream. Lost/incompatible checkpoints require controlled replay and discovery checks, not automatic reset.
6. Roll back by suspending the collector/stream/SQL schedule, redeploying compatible previous image and pinned transformation revisions, and resuming with preserved state. Schema/partition changes require a controlled migration, not runtime schema overwrite or reinterpretation. Before destroy, stop all workloads, preserve needed data/checkpoints/local state and warn that managed-table/storage deletion destroys recovery history; verify billable-resource cleanup.
